# Arynwood MCP 0.4.4 — Linux Desktop Alpha

## Packages

- `arynwood-mcp_0.4.4_amd64.AppImage`
- `arynwood-mcp_0.4.4_amd64.deb`
- `SHA256SUMS.txt`

Linux x86_64 only. Release artifacts are built on Ubuntu 22.04 with a glibc 2.35
baseline. Ollama, models, Qdrant and optional creative services are installed
separately. See [installation](../installation.md), [platform requirements](../supported-platforms.md)
and [known limitations](../known-limitations.md).

## Changes

- Fix `AppRun.wrapped: Permission denied` by making both AppImage launchers readable
  and executable by every user, then checking the finished archive.
- Build Linux releases on Ubuntu 22.04 instead of a moving runner to lower the
  glibc requirement; support that system's GStreamer plugin layout.
- Include AppStream catalog metadata and keep desktop/backend/package versions in sync.
- Include the chat, project, memory and knowledge changes listed in [CHANGELOG.md](../../CHANGELOG.md).

## Maintainer upload checklist

1. Use the tested Ubuntu 22.04 artifacts. Preserve their filenames and keep them
   beside the supplied `SHA256SUMS.txt`; run `sha256sum -c SHA256SUMS.txt` before upload.
2. Use the repository's tag convention, **`v0.4.4`**, for the 0.4.4 release. The
   prepared binary source commit is `429c49471f3c5a6132eac909adc2ed70497d4203`.
   Later documentation/workflow-only commits do not change those binaries.
3. A pushed `v*.*.*` tag starts the release workflow, which creates a **draft**
   release. Wait for it to finish before adjusting its assets or publishing it.
   A manual workflow run only uploads CI artifacts.
4. Attach both packages and the matching checksum file to the release. Copy the
   0.4.4 changelog section into its notes, retain the Linux alpha designation, and
   publish when ready. Avoid mixing locally built packages with the tested CI set.
5. After publication, download the release assets and check their hashes. Then
   request an AppImageHub retest of the catalog submission.

The Desktop release folder includes a validation report and a copy of release
notes for the manual upload. Preparing this folder does not create a tag or
publish a GitHub release.
